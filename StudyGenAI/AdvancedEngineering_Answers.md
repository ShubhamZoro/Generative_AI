## 1. FastAPI and API Design

### Overview
FastAPI is a modern, high-performance Python web framework for building APIs, built on top of Starlette (async web framework) and Pydantic (data validation). It automatically generates OpenAPI/Swagger documentation, uses Python type hints for input/output validation, and natively supports async/await, making it ideal for building AI serving APIs. A well-designed API follows REST principles, is versioned (`/v1/`, `/v2/`), uses appropriate HTTP methods and status codes, handles errors uniformly, and is idempotent where possible.

### How do you evaluate it?
Evaluating an API means measuring correctness, performance, and usability simultaneously. Functional testing validates that each endpoint returns correct responses for valid inputs, correct error codes for invalid inputs, and handles edge cases gracefully — tools like pytest with httpx or FastAPI's TestClient are ideal for this. Performance testing uses tools like Locust, k6, or Apache JMeter to simulate concurrent users and measure throughput (requests per second), latency percentiles (p50, p95, p99), and error rates under load. Contract testing with tools like Pact ensures the API fulfils the expectations of all its consumers without integration tests between every pair of services. API usability is evaluated by having consumers (frontend, mobile, other services) review the OpenAPI documentation for clarity and completeness. Security evaluation involves penetration testing — checking for injection vulnerabilities, authentication bypasses, and broken object-level authorization (BOLA), which is the most common API vulnerability per OWASP API Security Top 10.

### How do you monitor it?
API monitoring requires instrumenting every request at the middleware level. Using FastAPI middleware or Starlette middleware, you capture request duration, status codes, endpoint path, and request/response sizes, then export these as metrics to Prometheus. A Grafana dashboard visualizes request rate, error rate, and latency distributions (USE method: Utilization, Saturation, Errors). Distributed tracing with OpenTelemetry and Jaeger or Zipkin provides end-to-end visibility into how a single request flows across multiple services. Structured JSON logging (using Python's `structlog` or `loguru`) captures request context, user IDs, and correlation IDs for debugging. Alerting rules trigger PagerDuty or Slack notifications when error rate exceeds 1%, p99 latency exceeds the SLA threshold, or the service becomes unhealthy per health check endpoints (`/health`, `/ready`).

### How do you prevent failures?
Preventing API failures starts with defensive design. Input validation via Pydantic models ensures malformed requests are rejected at the boundary with informative 422 errors before reaching business logic. Rate limiting (using `slowapi` in FastAPI or an API gateway like Kong or AWS API Gateway) protects downstream services from traffic spikes. Circuit breaker patterns (using `aiobreaker` or Resilience4j if calling external services) prevent cascading failures when a dependency is degraded. Timeout enforcement on all outbound calls (database queries, external APIs, LLM calls) prevents threads from hanging indefinitely. Graceful shutdown handling ensures in-flight requests complete during deployments. Dependency injection with proper resource lifecycle management (database connections, HTTP clients) prevents connection leaks. Comprehensive unit and integration tests in CI catch regressions before deployment.

### How do you control costs?
API cost control centers on efficient resource utilization. Right-sizing the deployment — profiling actual CPU/memory usage under realistic load and selecting appropriately sized cloud instances — avoids over-provisioning. Auto-scaling (Kubernetes HPA or cloud-native auto-scaling groups) ensures you pay only for capacity actually needed, scaling in during low traffic and out during peaks. Response caching (using Redis with TTL) for deterministic or slowly changing endpoints reduces downstream computation cost. Connection pooling for database and external service connections reduces overhead per request. Async request handling via FastAPI's native async support allows a single worker process to handle many concurrent I/O-bound requests, improving throughput per dollar. Compression (gzip middleware) reduces egress bandwidth costs. Monitoring request patterns reveals unused or rarely-called endpoints that can be deprecated or consolidated.

### How do you deploy it safely?
Safe API deployment uses blue-green or canary deployment strategies. Containerize the FastAPI application with Docker using a multi-stage build to minimize image size (use a slim Python base image, copy only the application code and production dependencies). Run the container with Uvicorn workers managed by Gunicorn (`gunicorn -k uvicorn.workers.UvicornWorker`) for production stability. Use Kubernetes Deployments with `RollingUpdate` strategy — configuring `maxUnavailable: 0` and `maxSurge: 1` ensures zero-downtime updates. Liveness probes (`/health`) and readiness probes (`/ready`) ensure Kubernetes only routes traffic to healthy pods. Use ConfigMaps and Secrets (not hardcoded values) for configuration and credentials. Run database migrations as separate Jobs before deploying the new API version. A CI/CD pipeline (GitHub Actions, GitLab CI) runs tests, builds the Docker image, pushes to a container registry, and triggers the Kubernetes rollout only on the main branch.

## 2. Microservices and Distributed Systems

### Overview
Microservices is an architectural pattern where an application is decomposed into small, independently deployable services, each responsible for a specific business capability (e.g., user service, order service, AI inference service). In an AI/ML system, microservices might include a separate embedding service, vector search service, LLM gateway service, and orchestration service. Distributed systems are inherently challenging because of the CAP theorem (you can have at most 2 of: Consistency, Availability, Partition Tolerance), network partitions, partial failures, and eventual consistency challenges.

### How do you evaluate it?
Evaluating a microservices architecture involves both functional correctness and non-functional properties. At the service level, each service has its own independent test suite covering unit, integration, and contract tests. End-to-end tests validate critical user journeys across multiple services. Service-level agreements (SLAs) for each service — uptime percentage, latency guarantees — are defined and measured continuously. Chaos engineering (using tools like Chaos Monkey or Gremlin) deliberately injects failures (pod kills, network latency, disk full scenarios) to evaluate the system's resilience and identify failure modes before they occur in production. System-level evaluation measures overall throughput under realistic traffic patterns, including inter-service communication overhead.

### How do you monitor it?
Monitoring distributed systems requires the three pillars of observability: **metrics**, **logs**, and **traces**. Each service exports Prometheus metrics and logs structured JSON to a centralized log aggregator (Elasticsearch/Grafana Loki/Splunk). Distributed tracing with OpenTelemetry propagates trace context (trace ID, span ID) in HTTP headers and gRPC metadata across service calls, allowing Jaeger or Tempo to reconstruct the full request path across services. Service mesh solutions like Istio or Linkerd provide automatic mTLS, distributed tracing, and traffic management observability without application code changes. Service dependency maps (generated from trace data) show which services are critical paths and how latency in one propagates through the system. SLO (Service Level Objective) dashboards track error budget burn rates.

### How do you prevent failures?
Preventing failures in distributed systems requires embracing the reality that failures will happen and designing for resilience. The **bulkhead pattern** isolates critical services from non-critical ones using separate thread pools or resource quotas — a spike in the AI inference service doesn't starve the authentication service. **Circuit breakers** monitor failure rates for inter-service calls and "open the circuit" (fast-fail) when a dependency is degraded, preventing cascading failure while allowing periodic retries. **Timeouts** are mandatory on all network calls — never wait indefinitely. **Retry with exponential backoff and jitter** handles transient failures without thundering herd problems. **Idempotency** ensures that duplicate or retried requests don't cause unintended side effects. **Saga pattern** manages distributed transactions across services, using compensating transactions to undo partial operations if a step fails.

### How do you control costs?
Cost control in microservices starts with right-sizing services independently — a stateless embedding service can scale horizontally on small CPU instances, while GPU-intensive inference stays on dedicated GPU nodes. Namespace-level resource quotas in Kubernetes enforce per-team or per-service budget limits. Service autoscaling (HPA based on CPU/RPS, VPA for memory) ensures services scale down during off-peak hours. Event-driven architectures using message queues (Kafka, SQS) decouple producers from consumers and allow asynchronous processing that can be batched for efficiency, avoiding always-on synchronous dependencies. Shared infrastructure (like a central vector database or embedding cache) avoids duplicating expensive resources per service. Regularly profiling inter-service traffic with tools like Pixie or Hubble identifies unexpectedly chatty service-to-service communication patterns that waste network bandwidth and compute.

### How do you deploy it safely?
Deploying microservices safely requires treating each service as an independent deployment unit. Each service has its own CI/CD pipeline with independent versioning and deployment cadence. API versioning and backward-compatible contract changes (consumer-driven contract testing) ensure that deploying a new version of Service A doesn't break Service B. Use blue-green deployments or canary releases for high-traffic, high-risk services — route 5% of traffic to the new version, monitor error rates and latency, and automatically promote or roll back based on defined thresholds. Feature flags (using LaunchDarkly or a simple config service) decouple deployments from feature releases, allowing new behavior to be enabled/disabled without redeployment. For database schema changes, use the expand-contract pattern: add new schema changes (expand), deploy the new code, then remove old schema once all services have migrated (contract).

## 3. CI/CD Pipelines

### Overview
CI/CD (Continuous Integration / Continuous Deployment) is the practice of automating the build, test, and deployment of software to enable frequent, reliable releases. In ML/AI systems, CI/CD extends beyond traditional software to include data pipeline testing, model quality gates, and model deployment (MLOps CI/CD). A modern CI/CD pipeline triggers on every code push, runs a comprehensive test suite, builds deployment artifacts (Docker images, model packages), and deploys to production with appropriate safety gates.

### How do you evaluate it?
A CI/CD pipeline itself must be evaluated for effectiveness and reliability. Key metrics include: **pipeline pass rate** (what % of pipelines succeed on first run), **mean time to recover** (how long from a failing commit to a green pipeline), **deployment frequency** (how often you ship to production), and **lead time** (from code commit to production). These are the DORA (DevOps Research and Assessment) metrics. For ML pipelines specifically, evaluate whether model quality gates (accuracy thresholds, latency benchmarks) are meaningful and well-calibrated — gates that are too loose miss regressions; gates too strict block valid improvements. Pipeline execution time itself is evaluated; long pipelines (>20 minutes) discourage frequent commits and should be optimized with parallelism, caching, and selective testing.

### How do you monitor it?
Monitoring CI/CD pipelines involves tracking pipeline health at the platform level (GitHub Actions, GitLab CI, Jenkins) and at the individual job level. Dashboard tools (DataDog CI Visibility, GitHub Actions insights) show pipeline success rates, duration trends, and flaky test rates over time. Flaky tests — tests that randomly pass or fail — are particularly damaging to CI reliability and should be tracked and quarantined. Alert on sustained pipeline failure in main/master branches as a P1 incident — a broken main pipeline blocks all deployments. For ML pipelines, monitor training time, data preprocessing duration, and model artifact size trends. Deployment events (successful deploys, rollbacks) should be recorded as annotations on monitoring dashboards so engineers can correlate them with production metric changes.

### How do you prevent failures?
Preventing pipeline failures means investing in pipeline reliability and test quality. Pre-commit hooks (using `pre-commit`) run fast checks (linting, formatting, type checking) locally before code is pushed, catching simple issues early without consuming CI resources. Test pyramid discipline — many fast unit tests, fewer integration tests, minimal slow E2E tests — keeps pipelines fast and reliable. Dependency pinning (using `requirements.txt` or `poetry.lock` with exact versions) prevents "works today, fails tomorrow" failures caused by transitive dependency updates. Branch protection rules enforce that CI must pass before merging to main. For ML pipelines, data quality checks at pipeline entry validate that training data meets expected schema and statistical properties before expensive training jobs start. Infrastructure-as-code (Terraform) for the CI environment ensures reproducible, version-controlled pipeline infrastructure.

### How do you control costs?
CI/CD infrastructure costs can grow quickly with frequent pipelines and long jobs. Self-hosted runners on spot/preemptible instances (for non-critical builds) reduce cost vs. managed CI platforms. Aggressive caching of dependencies (Python packages, Docker layers, npm modules) between runs reduces job duration and compute cost. Conditional execution — only running GPU-intensive training jobs on direct commits to main, not on every feature branch PR — prevents wasteful resource consumption. For ML pipelines, implementing smart pipeline routing that only reruns model training when model code, hyperparameters, or a significant portion of the training data has changed (using DVC for data versioning) avoids expensive retraining for pure infrastructure changes. Job timeouts enforce spending limits — a runaway training job is killed after a max duration.

### How do you deploy it safely?
Safe CI/CD pipeline deployment means the pipeline itself is treated as code and deployed with rigor. CI configuration files (`.github/workflows/`, `.gitlab-ci.yml`, `Jenkinsfile`) are version-controlled, reviewed via pull requests, and tested with linting tools (`actionlint` for GitHub Actions). Secrets are stored in CI platform secret stores (GitHub Secrets, GitLab CI Variables, HashiCorp Vault) and never hardcoded in pipeline configuration. For ML deployments, implement a staged promotion model: `dev` → `staging` → `production`, with automated testing at each gate and manual approval required for production promotion. Implement automated rollback — if production health checks degrade after a deployment, the pipeline automatically reverts to the previous image/model version. Deployment locks prevent concurrent deployments to the same environment, avoiding race conditions.

## 4. Docker and Kubernetes

### Overview
Docker provides application containerization — packaging an application with all its dependencies into a portable, reproducible image. Kubernetes (K8s) is a container orchestration platform that automates deployment, scaling, load balancing, self-healing, and rolling updates of containerized applications. In AI/ML systems, Kubernetes manages inference server pods (possibly with GPU resources), preprocessing workers, API services, and supporting infrastructure, providing a unified control plane for the entire system.

### How do you evaluate it?
Evaluating a Docker/Kubernetes setup means validating both the correctness of configurations and runtime performance. Docker images are scanned with Trivy or Snyk for known CVEs in base images and dependencies. Image size is evaluated — smaller images reduce pull time and attack surface (aim for <500MB for most services, using multi-stage builds and `python:slim` or `distroless` bases). Kubernetes manifests are validated with `kubeval` and `kube-score` for best practices (resource requests/limits, liveness probes, non-root users). Cluster performance is evaluated through load testing that measures pod startup time (cold-start latency), time-to-scale (how quickly HPA provisions new pods), and resource efficiency (ratio of requested to actually used CPU/memory). For GPU workloads, evaluate GPU utilization with NVIDIA DCGM metrics to ensure pods are not underutilizing expensive GPU resources.

### How do you monitor it?
Kubernetes monitoring uses the kube-state-metrics exporter and cAdvisor (built into kubelet) to expose pod, node, deployment, and namespace metrics to Prometheus. The Grafana Kubernetes dashboards (from the community library) provide out-of-the-box visibility into node resource pressure, pod restarts, pending pods, and deployment rollout status. For GPU workloads, NVIDIA DCGM Exporter exposes GPU utilization, memory usage, temperature, and power draw per pod. Node-level monitoring catches disk pressure, OOM events, and network saturation. Pod-level monitoring alerts on excessive restarts (CrashLoopBackOff), OOM kills (which mean memory limits are too low), and Pending pods (which mean insufficient cluster capacity). The Kubernetes Events API provides real-time visibility into scheduling decisions, probe failures, and image pull errors.

### How do you prevent failures?
Preventing failures in Kubernetes requires defense in depth. Always set **resource requests and limits** for every container — requests allow Kubernetes to schedule intelligently; limits prevent a runaway container from starving its neighbors. Set requests equal to or slightly below typical usage, and limits 1.5–2x the request. **Liveness probes** restart containers that are deadlocked or stuck. **Readiness probes** prevent traffic from reaching pods that aren't yet ready to serve. **PodDisruptionBudgets** ensure that rolling updates or node maintenance never takes down more than a defined percentage of pods simultaneously. **Pod Anti-Affinity rules** spread replicas across nodes and availability zones to prevent a single node failure from taking down the service. Use **multi-AZ clusters** and **node auto-provisioner** (Karpenter) for resilient, elastic infrastructure. Keep Kubernetes and node OS versions updated to patch security vulnerabilities.

### How do you control costs?
Kubernetes cost control requires visibility and active optimization. Tools like Kubecost or OpenCost provide per-namespace, per-service, per-team cost breakdowns. Right-sizing pods using VPA (Vertical Pod Autoscaler) recommendations reduces over-provisioning. HPA (Horizontal Pod Autoscaler) scales to zero or near-zero during off-hours for non-critical services. **Spot/preemptible node pools** for fault-tolerant workloads (batch jobs, non-latency-critical inference) achieve 60–80% cost savings vs. on-demand instances. Node consolidation with Karpenter or Cluster Autoscaler's consolidation mode bins workloads onto fewer, fuller nodes during quiet periods and terminates underutilized nodes. For GPU nodes (the most expensive), maximize GPU utilization with NVIDIA time-slicing or MIG (Multi-Instance GPU), allowing multiple pods to share a single GPU. Use Reserved Instances (1 or 3-year commitments) for baseline steady-state load and spot for burstable capacity.

### How do you deploy it safely?
Safe Kubernetes deployments use GitOps — all Kubernetes manifests are stored in a Git repository, and an operator like ArgoCD or Flux continuously reconciles the cluster state with the repository. This ensures every cluster change is version-controlled, peer-reviewed, and auditable. Deployments use `RollingUpdate` strategy with `maxUnavailable: 0` (no downtime) and appropriate `minReadySeconds` to bake new pods before proceeding. Canary deployments using Argo Rollouts or Flagger automatically route a small percentage of traffic to the new version, monitor error rates and latency, and either promote or roll back automatically. Kubernetes RBAC (Role-Based Access Control) restricts who can deploy to production. Network policies enforce that only authorized services communicate with each other. Image promotion workflows ensure only images that passed CI (tagged with a specific label or SHA) can be deployed to production — never `latest` tags.

## 5. System Design

### Overview
System design for AI applications involves architecting scalable, reliable, and maintainable systems that handle complex AI workflows — from data ingestion and preprocessing through model serving, result caching, and user-facing APIs. Good system design considers load characteristics (read-heavy vs. write-heavy, latency-sensitive vs. throughput-oriented), data flow, component interactions, scalability bottlenecks, and failure modes. For AI systems, unique considerations include GPU resource management, long-running inference requests, streaming responses, and the need to update models without downtime.

### How do you evaluate it?
System design is evaluated along multiple dimensions. **Functional correctness**: Does the system correctly implement the required features end-to-end? **Scalability**: Can the system handle 10x or 100x current traffic by scaling horizontally? Identify bottlenecks using load testing and flame graphs. **Reliability**: What is the system's achievable SLA? Fault injection testing (chaos engineering) reveals single points of failure. **Latency**: Do p50, p95, and p99 latencies meet the SLA under realistic traffic? **Consistency and correctness**: Are there race conditions, data inconsistencies, or idempotency violations? **Maintainability**: Is the system modular, well-documented, and easy for a new engineer to understand and modify? Design review sessions (architecture reviews, threat modeling) with cross-functional teams provide qualitative evaluation against business requirements.

### How do you monitor it?
System-level monitoring uses the four golden signals from the Google SRE book: **Latency** (request duration, distinguishing successful vs. failed requests), **Traffic** (requests per second, tokens generated per second for LLM systems), **Errors** (error rate by type — 4xx, 5xx, timeout, model error), and **Saturation** (how close to capacity is each resource — GPU utilization, DB connections, queue depth, memory). Each component (API gateway, inference service, database, cache, queue) exposes these metrics to Prometheus. Synthetic monitoring (scheduled canary requests from an external source) detects issues independently of internal telemetry and validates end-to-end system health from the user's perspective. Business metrics (active users, task completion rate, revenue per request) are the ultimate measure of system health and should be tracked alongside technical metrics.

### How do you prevent failures?
Preventing system-level failures requires designing for resilience from the start, not as an afterthought. Apply **graceful degradation** — if the AI inference service is down, serve cached results or a simplified fallback rather than an error page. Implement **timeouts everywhere** — every network call, database query, and external API call must have a defined maximum wait time. Use **asynchronous communication** (message queues) between non-latency-critical components to decouple producers from consumers and absorb traffic bursts. Implement **idempotency keys** for all write operations to safely handle duplicate requests from retries. Conduct **game days** — planned failure drills where the team deliberately breaks components in production-like environments to test runbooks and detection capabilities. Maintain up-to-date **runbooks** for every alert so on-call engineers can diagnose and resolve issues quickly.

### How do you control costs?
System-level cost control requires understanding the cost structure of each component. For AI systems, GPU inference is typically the dominant cost — maximize GPU utilization through batching, model optimization, and caching. A **tiered architecture** routes requests based on complexity: simple requests to cheap, fast models; complex requests to expensive, powerful models. **Caching at every layer** (semantic caching for LLM calls, Redis for API responses, CDN for static assets) reduces redundant computation. **Usage-based billing awareness** — monitor per-user or per-team token consumption and implement quota enforcement to prevent runaway costs. **Architecture ADRs (Architecture Decision Records)** include cost implications, and system design reviews evaluate cost at the design stage rather than after deployment. Regular cost reviews correlate architecture changes with billing changes.

### How do you deploy it safely?
Safe system deployment for complex AI systems requires a multi-stage strategy. Start with **blue-green deployment** for major system changes — run the new version alongside the old version, and switch traffic atomically. For continuous iteration, use **canary deployments** — route 1% → 5% → 25% → 100% of traffic progressively, with automated promotion based on error rate and latency gates. **Feature flags** decouple code deployment from feature activation, allowing instant kill switches for problematic features without redeployment. **Database migration discipline**: use backward-compatible schema changes, and test migrations against a production-sized copy of data before applying to production. **Comprehensive E2E smoke tests** run automatically after every deployment to validate critical paths. **Rollback playbooks** are documented, tested, and rehearsed so rollback can happen in under 5 minutes if needed.

## 6. Evaluation and Observability

### Overview
Evaluation determines whether an AI system is performing correctly and meeting quality standards. Observability is the property of a system that makes it possible to understand its internal state from its external outputs (metrics, logs, traces). Together, they form the foundation of trustworthy AI systems in production. For LLM-based systems, evaluation extends beyond traditional software metrics to include semantic quality, faithfulness, relevancy, and safety dimensions that require specialized tooling.

### How do you evaluate it?
Evaluation for AI systems must happen at multiple levels. **Offline evaluation** uses a benchmark dataset with known-good answers to measure accuracy, F1, BLEU/ROUGE (for text generation), or domain-specific metrics (code execution pass rate for code generation). **Online evaluation** uses production traffic to measure business KPIs (task completion rate, user rating, click-through rate). **LLM-as-a-judge** evaluation uses a powerful LLM (GPT-4) to automatically evaluate response quality across dimensions like helpfulness, accuracy, harmlessness, and adherence to instructions — scalable but needs periodic validation against human ground truth. **Human evaluation** for a sampled subset of responses provides the highest-quality signal and calibrates automated metrics. For RAG systems, RAGAS provides metrics for faithfulness, answer relevancy, context precision, and context recall. Evaluation should be continuous — run on a scheduled basis or triggered by production data samples.

### How do you monitor it?
Observability in AI systems requires instrumenting the entire pipeline, not just the API layer. For LLM systems: log every prompt (with PII redaction), the retrieved context (for RAG), the generated response, latency breakdown by component (retrieval latency, LLM latency, total latency), and token counts (for cost tracking). Structured logging (JSON format) allows these to be queried and aggregated in log analytics tools. Metrics dashboards track LLM error rates (API timeouts, content filter triggers, context length exceeded), cache hit rates, and queue depths. Trace each request with a unique request ID that propagates through all components, enabling full reconstruction of a request's journey. Production monitoring tools like Arize, WhyLabs, and LangSmith are purpose-built for LLM observability, providing drift detection, quality monitoring, and debugging capabilities over model inputs and outputs.

### How do you prevent failures?
Preventing evaluation and observability failures means ensuring your monitoring infrastructure is more reliable than the system it monitors. Use redundant monitoring pipelines — if your primary Prometheus scrape fails, an alternate monitoring path must still capture critical metrics. Implement **dead man's switches** — a monitor that alerts if it stops receiving telemetry from a service (silence detection). For LLM quality, implement **guardrails** that check model outputs for safety, format adherence, and relevance before serving them to users — a second model (NeMo Guardrails, Llama Guard) can classify responses as safe/unsafe in real time. Automated regression testing on evaluation benchmarks prevents silent quality degradation when models, prompts, or retrieval systems change. Alert on sudden changes in evaluation metric distributions, not just hard thresholds.

### How do you control costs?
Observability itself has a cost — ingesting, storing, and querying high-cardinality metrics, logs, and traces at scale is expensive. Apply **sampling strategies**: trace 100% of error requests and a configurable sample (e.g., 1–10%) of successful requests, reducing trace storage cost by orders of magnitude. Use **metrics aggregation** — instead of recording raw data for every request, compute histograms and summary statistics before export. Implement **log tiering** — structured logs for recent data (7 days in hot storage), compressed logs for older data (30 days in warm storage), and archival for compliance (1 year in cold storage like S3 Glacier). Evaluate per-evaluation-run cost for LLM-as-a-judge systems and use cheaper judge models (GPT-3.5, Claude Haiku) for high-volume quality checks, reserving expensive models for difficult cases. Set retention policies aggressively and delete data that provides no value beyond its retention window.

### How do you deploy it safely?
Deploying observability changes safely means treating monitoring configuration as code with the same rigor as application code. Prometheus alert rules, Grafana dashboards, and log parsing pipelines are stored in version control. Alert rule changes are reviewed in pull requests — poorly written alerts cause alert fatigue (too many false positives) or blind spots (important failures go undetected). Before deploying new evaluation logic or metrics, validate them on historical data to ensure they produce expected results. When deploying a new model or application version, keep existing dashboards and alerts running without modification for a bake-in period (24–72 hours) before updating baselines. Use A/B comparison dashboards during deployments to directly compare old vs. new version behavior side by side.

## 7. RAG Architecture Trade-offs

### Overview
RAG (Retrieval-Augmented Generation) systems combine vector search for document retrieval with LLM generation, and each architectural choice involves significant trade-offs. The key design decisions include: choice of embedding model, chunking strategy, vector database, retrieval algorithm (dense, sparse, hybrid), reranking approach, context injection method, and how to handle multi-hop questions, multi-document reasoning, and freshness requirements. Understanding these trade-offs is essential for designing a RAG system appropriate for a given use case.

### How do you evaluate it?
RAG evaluation decomposes into retrieval quality and generation quality. For retrieval: **Context Precision** (fraction of retrieved chunks that are actually relevant — measures noise in retrieval), **Context Recall** (fraction of relevant information that was retrieved — measures coverage), and **Mean Reciprocal Rank (MRR)** (position of the first relevant result in the ranking) are the primary metrics, measurable with RAGAS or a custom evaluation pipeline. For generation: **Faithfulness** (does the answer accurately reflect only information in the retrieved context — no hallucination?), **Answer Relevancy** (does the answer address the question?), and **Answer Correctness** (factual accuracy vs. a gold standard answer). Evaluate both components independently — poor overall system performance could be a retrieval problem or a generation problem, and they require different fixes. Regression test suites with diverse, representative queries from real users provide the most actionable insights.

### How do you monitor it?
Monitoring a RAG system in production requires tracing each request through both the retrieval and generation stages. Log the query embedding, the top-k retrieved chunk IDs and their similarity scores, the full assembled prompt, and the generated response — all linked by a request ID. Track retrieval latency, LLM latency, and total end-to-end latency separately (retrieval latency spikes indicate vector database issues; LLM latency spikes indicate model provider issues). Monitor the distribution of top-1 similarity scores — if average similarity drops over time, it may indicate the knowledge base is becoming stale relative to evolving user queries (a form of data drift in the retrieval context). User feedback (thumbs up/down, explicit corrections) linked to specific retrievals provides ground truth for continuous quality improvement. Alert on sudden spikes in low-similarity retrievals or high rates of "I don't know" responses.

### How do you prevent failures?
RAG failure modes include: no relevant chunks retrieved (leading to hallucination or "I don't know"), irrelevant chunks retrieved (polluting the context window), context length overflow (too many chunks exceed the LLM's context limit), chunking artifacts (important information split across chunk boundaries), and stale knowledge base. Prevent "no relevant chunks" failures by setting a minimum similarity threshold and implementing fallback behavior (broader search, keyword search fallback). Prevent context overflow by implementing a token budget system that dynamically selects the maximum number of chunks that fit within a safe context limit. Prevent stale knowledge by implementing automated ingestion pipelines that update the vector store whenever source documents change. Test the system against adversarial queries — questions that no document can answer — to ensure it says "I don't know" rather than hallucinating.

### How do you control costs?
RAG costs come from three sources: embedding API calls (for indexing and query embedding), vector database storage/query costs, and LLM generation costs. Reduce embedding costs by using smaller, cheaper embedding models (all-MiniLM-L6-v2 instead of text-embedding-ada-002) — often with minimal quality loss. Cache embeddings of frequently repeated queries to avoid re-embedding. For the vector database, choose a cost-appropriate tier — self-hosted Chroma or Qdrant for smaller scale, managed Pinecone or Weaviate for production scale. Control LLM generation costs by minimizing the context window used — only include the top-2 or top-3 chunks instead of top-10, as additional chunks often add noise rather than value. Semantic caching of query-response pairs avoids end-to-end RAG pipeline cost for repeated questions. Monitor cost per query and track the contribution of each pipeline stage.

### How do you deploy it safely?
RAG deployment safety requires handling both the application code and the knowledge base state. Version the embedding model and vector store index together — upgrading the embedding model requires reindexing all documents, and the old and new indices are incompatible. Use blue-green deployment for the vector store: build the new index alongside the old one, switch traffic after validation, and keep the old index for rollback. When updating source documents (adding, modifying, deleting), process changes asynchronously through an ingestion queue (Kafka or SQS) rather than blocking the query path. Implement per-document access control in the vector store metadata to ensure users only retrieve documents they're authorized to see. Validate new document ingestion with automated quality checks — if a document is parsed incorrectly (corrupt PDF, encoding issue), detect and flag it rather than silently ingesting garbage.

## 8. Agent Orchestration and State Management

### Overview
AI agents are systems where an LLM autonomously plans, takes actions using tools, observes results, and iterates toward a goal. Agent orchestration involves managing the control flow — the ReAct (Reason + Act) loop, tool selection, state persistence, and error recovery. State management is the hardest problem: agents need to maintain context across long multi-step tasks, potentially across multiple LLM calls, tool invocations, and even system restarts. Frameworks like LangGraph, AutoGen, and CrewAI provide infrastructure for building stateful, multi-agent systems.

### How do you evaluate it?
Evaluating agents is significantly harder than evaluating single-turn LLMs because agents take sequences of actions, and intermediate steps matter as much as final outcomes. Evaluation metrics include: **Task completion rate** (what fraction of tasks does the agent successfully complete?), **Step efficiency** (does the agent complete tasks in the minimum number of steps, or does it take unnecessary detours?), **Tool call accuracy** (does the agent select the right tools with correct parameters?), and **Failure recovery rate** (when a tool call fails, does the agent recover gracefully?). Evaluation environments must be reproducible — tools and external APIs should be mocked so agent behavior can be deterministically tested. LangSmith, AgentBench, and custom evaluation harnesses allow multi-step agent evaluation at scale. Human evaluation of agent trajectories (the full sequence of reasoning and actions) reveals failure modes that outcome metrics alone miss.

### How do you monitor it?
Monitoring agents requires tracing every step of the agent loop, not just the final output. Each agent invocation generates a trace: the initial goal, each reasoning step (LLM call with input/output), each tool call (name, parameters, result), and the final output — all with timestamps and durations. This trace is the fundamental unit of agent observability. Tools like LangSmith, Weights & Biases Weave, and Phoenix (Arize) are designed specifically for LLM/agent tracing. Monitor: **agent success rate** (task completed vs. failed), **mean steps per task** (increasing steps may indicate degrading planning ability), **tool error rate** (persistent tool failures need investigation), **context length consumption per task** (approaching context limit causes truncation and task failure), and **wall clock time per task** (runaway agents need timeout protection). Alert on tasks that run for more than a configured maximum duration.

### How do you prevent failures?
Preventing agent failures requires extensive guardrailing at every step. Implement **maximum step limits** — after N steps without completing the task, the agent must halt and return its best partial result or ask for human guidance rather than looping indefinitely. **Tool input validation** checks parameters before passing them to potentially dangerous tools (file system, database, external APIs). **Reversibility checks** — before taking irreversible actions (sending emails, making purchases, deleting records), require explicit human confirmation. **Sandboxed tool execution** — run code-execution tools in isolated containers with network access restrictions to prevent malicious or buggy code from causing damage. **Checkpoint state persistence** saves agent state at each step so it can be resumed from the last checkpoint on failure rather than starting from scratch. **Prompt injection defenses** — treat all retrieved or user-provided content as untrusted when constructing tool call parameters.

### How do you control costs?
Agent costs are multiplicative — a single user request may trigger dozens of LLM calls and tool invocations. Cost control starts with **maximum budget enforcement**: track total LLM token usage and tool API calls per agent run, and halt the agent if the budget is exceeded. **Model routing** uses cheap, fast models (Claude Haiku, GPT-3.5) for simple reasoning steps and expensive models only for complex planning or synthesis steps. **Tool call caching** — if the agent calls the same search query or API endpoint multiple times within a run, return the cached result. **Plan-first architectures** reduce unnecessary tool calls by having the agent produce a full plan before executing it, catching errors in planning rather than mid-execution. **Parallel tool execution** — when multiple independent tool calls are needed, execute them concurrently rather than sequentially, reducing wall-clock time and the number of subsequent LLM reasoning steps needed.

### How do you deploy it safely?
Deploying agents safely requires strict operational boundaries. Define a **minimal privilege toolset** — only give the agent access to tools it strictly needs for its defined purpose, not a maximal set. Implement **tool call rate limiting** per agent run and per user to prevent abuse. Use **async task queues** (Celery, RQ, Temporal) to manage long-running agent tasks — submit the task, return a job ID, and let the user poll for results rather than blocking an HTTP connection. **Human-in-the-loop checkpoints** for high-stakes actions: the agent pauses, presents its planned action to a human, and waits for approval before proceeding. **Canary deployments** of agent updates — route a small percentage of tasks to the updated agent, compare outcomes with the current version, and promote only if quality metrics improve. Maintain full audit logs of all agent actions (what it read, what it called, what it changed) for compliance and debugging.

## 9. Failure Handling and Retries

### Overview
In distributed AI systems, failures are the norm, not the exception. Network partitions, API rate limits, transient timeouts, hardware faults, and downstream service degradations all cause request failures. Effective failure handling distinguishes between transient failures (safe to retry) and permanent failures (where retrying would be futile or harmful). The goal is to build systems that handle failures gracefully — recovering automatically when possible, degrading gracefully when not, and always providing meaningful, actionable responses to users and operators.

### How do you evaluate it?
Evaluating failure handling requires deliberately introducing failures in a controlled environment. **Unit tests** simulate specific failure modes by mocking dependencies to return errors, timeouts, and corrupted responses — verify the code handles each case correctly. **Chaos engineering** with tools like Chaos Monkey, Gremlin, or Chaos Toolkit introduces real failures into staging or production environments: kill pods, delay network packets, saturate disk I/O, and cut database connections. Measure the system's response: Did the circuit breaker open? Did retries eventually succeed? Did fallbacks activate? Did the user receive a graceful error rather than a raw exception? **Retry logic correctness** tests verify idempotency — that retrying a failed write operation doesn't create duplicate records. Evaluate **Mean Time to Recovery (MTTR)** for various failure scenarios to ensure recovery mechanisms are fast enough.

### How do you monitor it?
Monitoring failure handling requires visibility into not just errors but also the behavior of error-handling mechanisms. Track **retry attempt counts** — a sudden spike in retries indicates a degrading dependency. Track **circuit breaker state transitions** (closed → open → half-open → closed) — an open circuit is a critical alert indicating a service is down. Track **dead letter queue (DLQ) depth** — messages that have exhausted all retries land in the DLQ; a growing DLQ indicates systematic failures that need investigation. Monitor **fallback activation rate** — if fallbacks are being used frequently, the primary path is unreliable and needs attention. Log every retry attempt with context (which request, which attempt number, what error was encountered, how long was the backoff) to enable post-incident analysis. Alert on sustained high retry rates, circuit breaker openings, and growing DLQ depth.

### How do you prevent failures?
The best failure handling is preventing failures from occurring. **Health checks** on all dependencies at startup fail fast if required services are unavailable rather than partially starting and failing unpredictably. **Dependency timeouts** enforce that no single dependency can block a service indefinitely. **Connection pooling with pool exhaustion protection** prevents "connection refused" errors by limiting the total number of concurrent connections and queuing excess requests rather than rejecting them. **Graceful degradation design** means that for every critical feature, there is a defined lower-fidelity fallback — cached response, simplified output, or informative error message — that activates automatically when the primary path fails. **Idempotent API design** ensures that duplicate or retried requests have the same effect as a single request, making retry safe. **Pre-production load testing** with realistic failure injection validates that failure handling works before it's needed in production.

### How do you control costs?
Poorly designed retry logic can dramatically amplify costs during degraded conditions. **Exponential backoff with jitter** ensures that retrying clients don't all retry at the same interval, which would create cascading retry storms that overwhelm already-struggling services. Cap the maximum retry delay (e.g., 60 seconds) to prevent requests from waiting too long. **Retry budgets** limit the total number of retries per request (typically 2–3 retries maximum) to bound the multiplicative cost amplification. **Circuit breakers** that open after a defined failure threshold prevent retrying a service that is clearly down — retrying a down service wastes compute without hope of success. For LLM API calls, which are expensive per token, never retry on authentication errors (permanent) or content policy violations (permanent) — only retry on transient errors (timeout, 429, 500, 503). Dead letter queues allow failed messages to be processed asynchronously during off-peak hours, reducing retry cost.

### How do you deploy it safely?
Deploying changes to failure handling logic requires particular care — bugs in retry logic or circuit breaker configuration can make outages worse rather than better. Deploy failure handling changes with **feature flags** so they can be quickly disabled if they cause unexpected behavior. **Test retry and circuit breaker behavior explicitly** in the CI pipeline using fault injection tests — don't assume it works. When changing retry parameters (backoff coefficients, max attempts, timeout values), change one parameter at a time and monitor the impact in staging before production. Validate that **idempotency guarantees** are preserved through any database or API changes deployed alongside the retry logic changes. During major incident response, have predefined **break-glass procedures** that can override circuit breakers, increase retry limits, or route around failing components — and ensure these procedures are documented in runbooks and tested periodically.
